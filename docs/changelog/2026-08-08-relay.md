# Kalshi WebSocket relay and status-pill consolidation (2026-08-08)

**Date:** 2026-08-08
**Type:** ops + UI
**Status:** shipped + pushed (commit pending)

## What changed

The prediction-market-lab CF Worker can't auth Kalshi's WebSocket because CF
Workers' `new WebSocket(url)` constructor (and the
`fetch(url, { Upgrade: "websocket" })` path) don't support
custom headers on the outbound upgrade. This step ships
the relay that fixes it, plus consolidates the two "connection"
pills at the top of the dashboard.

### Kalshi WebSocket relay (the unblocker)

A standalone Python service at `prediction-market-lab/relay/` that:
1. Accepts an unauthenticated WS from the CF Worker
2. Signs the WS path with the demo creds (RSA-PSS, SHA-256, saltLength 32 — Kalshi's spec)
3. Opens an authed WS to Kalshi
4. Forwards messages bidirectionally

Files:
- `relay/server.py` — the relay. ~30 lines of `websockets` + `cryptography`.
- `relay/Dockerfile` — `python:3.12-slim` + the deps + the server. Runs as non-root.
- `relay/requirements.txt` — `websockets>=12.0,<14.0` + `cryptography>=42.0,<46.0`.
- `relay/fly.toml` — Fly.io app config. `shared-cpu-1x`, 1GB RAM, $1.94/mo. With the user's $0.83 free credit, ~12 days are free.
- `relay/deploy.sh` — one-time setup (`fly launch --no-deploy` + `fly secrets set` + `fly deploy`).
- `relay/README.md` — full deploy guide, local-dev option (cloudflared tunnel), security notes, cost breakdown.

**Why this works:** CF Workers can't add auth headers, but the relay runs in a Python runtime where the `websockets` library natively supports `extra_headers` (a list of tuples). The relay forwards the bot's WS to Kalshi with the right auth.

**Bug caught during testing:** the first iteration used `PKCS1v15` padding. Got HTTP 401. Kalshi requires **RSA-PSS with saltLength = 32 (SHA-256 digest length)**. The Prediction Market Lab Python tool (`kalshi_auth.py`) and the prediction-market-lab TS code (`src/kalshi/auth.ts`) both already use PSS — caught the relay by mismatch. Fixed and confirmed working: subscription ack `{"type":"subscribed","id":1,"msg":{"channel":"ticker","sid":1}}` came back from Kalshi via the relay.

**End-to-end smoke (deployed locally):**
```
$ KALSHI_KEY_ID="..." KALSHI_PRIVATE_KEY="..." python server.py
[INFO] kalshi-relay: starting relay on 0.0.0.0:8765
[INFO] websockets.server: server listening on 0.0.0.0:8765
[INFO] kalshi-relay: relay ready

# test client
$ websockets.connect('ws://127.0.0.1:8765/')
→ {"type":"subscribed","id":1,"msg":{"channel":"ticker","sid":1}}
```

### Point the bot at the relay

Once the relay is deployed, switch the bot via `POST /api/pm/bot/start`:

```bash
curl -X POST 'api/pm/bot/start' \
  -H "Content-Type: application/json" \
  -d '{"url": "wss://prediction-market-lab-relay.fly.dev/"}'
```

`wrangler.jsonc` has a commented-out `KALSHI_WS_RELAY_URL` env var that the bot can also pick up automatically (left commented until the relay is deployed).

### Pill consolidation ( UI fix)

The user flagged that the brand bar had two "connection" pills at the top:
- The  `stage-badge` (what the bot is doing)
- The  `live-indicator` (whether the dashboard is refreshing)

**Fix:** removed the `live-indicator` from the brand bar; moved it to a subtle corner dot at the bottom-right of the screen (the existing controls button sits at bottom-right, so the dot sits 4px above it). Tooltip on hover shows the last refresh time. The dot pulses green/amber/red but is much less prominent than the stage badge.

CSS:
- `.live-dot-corner` — fixed position, bottom-right, blurred background, 4px above the controls bar
- `.live-dot-corner-dot` — the actual dot, 7x7
- `.live-dot-corner-tooltip` — small mono-font text, max 320px, ellipsis
- `prefers-reduced-motion` respected (no pulse animation when set)

The stage badge is now the single primary "what is the bot doing" indicator at the top.

### Deploy steps (user runs from `prediction-market-lab/relay/`)

```bash
# 1. Install the fly CLI.
brew install flyctl

# 2. Set the account token (machine token in
#    the project-local `prediction-markets-env.txt`
#    is scoped to one app — for fly launch you need an account token).
export FLY_API_TOKEN="<your-fly-account-token>"

# 3. Deploy.
./deploy.sh
```

The script:
1. `fly launch --no-deploy` (creates the app)
2. `fly secrets set KALSHI_KEY_ID KALSHI_PRIVATE_KEY` (uploads the demo creds)
3. `fly deploy` (builds + ships)
4. Prints the smoke test + the URL

To update later: `./deploy.sh --update`.

### Free alternative (Mac + cloudflared)

For dev/testing without paying Fly.io: run the relay on the Mac, expose via cloudflared. The relay code is identical. See `relay/README.md` for the one-paragraph setup.

### What's next

The relay isn't deployed yet (user-side deploy). When the user runs `./deploy.sh`, the bot can be switched to the relay URL via `/start`. The whole "live numbers updating without pushing buttons" flow becomes automatic.

The CF Worker still tries to open the WS via the direct URL (which doesn't work for auth, but it's the fallback). Once the relay is deployed, the URL flips to the relay.
