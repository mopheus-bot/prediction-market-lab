# Cron jobs (2026-08-08)

The 4 scheduled jobs (scan / news / daily / train) land. A
single Worker `scheduled` handler dispatches by cron
expression to the right job. Every run is recorded in the
`cron_runs` D1 table for observability. The scan job is
fully implemented; the news, daily, and train jobs are
shipped with their core logic and the LLM/external
dependencies stubbed for steps 6/8.

## What ships

### New modules

- `src/cron/scan.ts` — pure math: `computeRealizedVol`,
  `scoreMarket`, `rankCandidates`. Mirrors
  `Prediction Market Lab/.../live/scan.py`.

- `src/cron/category-mapper.ts` — `mapCategory(category) → Vertical`.
  Mirrors the Python `category_mapper.py`. Single source of
  truth so the scan + bot agree on verticals.

- `src/cron/scan-cron.ts` — `runScanCron(env)`. Fetches the
  open events + markets via `KalshiClient`, iterates per
  market + fetches the recent trades, computes the
  candidate score, ranks, and writes the top N to the
  `scans` D1 table. Full implementation: works against the
  live Kalshi API.

- `src/cron/news-cron.ts` — `runNewsCron(env)`. Iterates the
  open positions in D1 and records a `llm_calls` row per
  position. The actual LLM call (mmx) and Telegram bridge
  land in. For  we just establish the
  schedule + observability.

- `src/cron/daily-cron.ts` — `runDailyCron(env)`. Aggregates
  the last 24h of trades, signals, and PnL; writes a
  summary JSON to R2 at `daily-recap/YYYY-MM-DD.json`.
  Per-vertical breakdown included.

- `src/cron/train-cron.ts` — `runTrainCron(env)`. Records a
  "train requested" entry. Optionally POSTs to
  `TRAIN_WEBHOOK_URL` (env) for external retrain pipelines.
  The full CF Workflow integration lands in.

- `src/cron/dispatcher.ts` — `jobForCron(cronExpression) →
  CronName`, `dispatchScheduledEvent(cronExpression, env)`,
  the `CRON_TABLE` constant, and the `recordRun(env, run)`
  helper. The dispatcher is the single entry point for
  scheduled events.

### Updated

- `src/index.ts` — `Env` extends `CronEnv` (so the cron jobs
  have the same env shape). Added the `scheduled` handler
  that delegates to `dispatchScheduledEvent` inside
  `ctx.waitUntil` (so the scheduler's response is fast
  even if the job runs for 60+ seconds).

- `wrangler.jsonc` — added `triggers.crons` with the 4
  expressions: `*/15 * * * *` (scan), `0 */6 * * *`
  (news), `0 6 * * *` (daily), `0 0 * * 0` (train).
  These must match `CRON_TABLE` in `dispatcher.ts`; the
  dispatcher fails fast if they drift.

### Optional env vars

- `SCAN_TOP_N` (default 25)
- `SCAN_LOOKBACK_HOURS` (default 24)
- `SCAN_MIN_TRADES` (default 10)
- `SCAN_VOL24H_MIN` (default 0)
- `SCAN_SERIES` (comma-separated Kalshi series; when set,
  the scan is series-anchored instead of full-market)
- `TRAIN_WEBHOOK_URL` (optional external retrain target)

## Why a single Worker for all 4 crons

Cloudflare allows one `scheduled` handler per Worker
service. Four separate Workers would mean four deploy
units, four CF Access policies, four sets of bindings,
and four cost lines. The dispatcher pattern keeps
everything in one place: each cron expression fires the
same `scheduled(event, env, ctx)` method, which routes to
the right job by inspecting `event.cron`. The `CRON_TABLE`
constant is the single source of truth for the schedule.

## Operational notes

- **Costs:** scheduled events themselves are free; only
  the actual compute (Worker CPU time, D1 writes, R2
  reads/writes, Kalshi API calls) bills. Each cron is
  designed to stay under 60 seconds and well under the
  $5/mo Workers Paid base.
- **Kalshi rate limits:** the scan caps at 500 markets
  per run and 5 pages of trades per market (5,000
  trades). Well under the public REST rate limit.
- **Idempotency:** the `scans` table is append-only; the
  `cron_runs` table is append-only. The daily cron writes
  `daily-recap/<date>.json` once per day (re-runs
  overwrite, which is fine for a daily recap).
